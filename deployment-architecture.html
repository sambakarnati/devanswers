Deployment · single EC2 host

How DevAnswers gets from a git repo to a running app

sambakarnati/devanswers @ main EC2 · Amazon Linux 2023 3.85.206.101 Docker 25.0

Both containers are built and run on a single EC2 instance — no registry, no CI pipeline. The diagram below is the thing to check before changing anything here: which arrows are fixed at build time versus run time, and which boundary a given failure actually crossed.

Mechanism notes

No registry, no CI
The repo is git cloned straight onto the EC2 host, and both docker builds run there. Shipping a change means pulling the new commit and rebuilding on that box — there's no image to push anywhere else.
Build-time vs. run-time config
Vite inlines VITE_API_BASE_URL when the frontend image is built (--build-arg), so changing the API host means rebuilding that image. The backend's secrets are the opposite: injected at docker run --env-file .env, so rotating a key only needs a container restart.
The .env PORT gotcha
The backend image sets ENV PORT=8080, but --env-file overrides it with whatever PORT the local .env holds. This deployment's .env came from a dev machine with PORT=5011, which silently moved the app off the mapped port until pinned with -e PORT=8080.
Two origins, no reverse proxy
The browser loads the app from :3000 and calls the API on :8080 directly — there's no nginx layer unifying them into one origin. That's why cors() is enabled in src/app.js; collapsing to a single origin later would let it come out.
Two access-control layers, not one
The EC2 security group only governs traffic to the instance itself. MongoDB Atlas keeps its own IP allow-list on top of that — the exact gap that produced a MongooseServerSelectionError the first time this stack came up, before the instance's IP was added in Atlas.
